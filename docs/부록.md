### A-1. 추론 백엔드를 HuggingFace transformers로

**처음 계획** vLLM으로 8B 모델을 4bit로 올리는 것이었다.

**일지에 적힌 과정** 처음 쓰려던 `kakaocorp/kanana-1.5-8b-instruct-2505`는 AWQ 양자화가 되지 않았다. Colab에서 양자화해 넘기는 방법을 적었다가, 그 모델을 쓸지도 정하지 않았다며 아무 모델이나 양자화해 보기로 했다. `Qwen3-VL-8B-Instruct`를 포함해 여러 모델이 실패했다. 4B 모델로 테스트하니 context length 문제로 오류가 났고, `max_model_len=4096`을 설정하자 추론은 되지만 여러 문장을 추론하는 중에 메모리 부족으로 종료됐다. bitsandbytes 양자화로 바꾸자 vLLM 웜업 단계에서 메모리가 부족하다는 오류가 났다. 4B 모델을 4bit로, `max_model_len=2048`로 설정했는데도 메모리를 12GB씩 차지해서 vLLM을 버렸다.

같은 과정에서 vLLM과 llama.cpp의 차이를 정리했다. vLLM은 속도와 처리량이 중점이라 환경이 맞을 때 최고의 성능을 내고, llama.cpp는 적응성이 중점이라 NVIDIA가 아니거나 GPU가 없거나 Mac 같은 다양한 환경에서 추론할 수 있다.

HuggingFace로 옮긴 뒤에도 `Qwen3-VL-8B-Instruct`는 실패했다. VL 모델은 멀티모달이라 고유한 아키텍처 코드를 가진 경우가 많아 `trust_remote_code=True`를 추가하고 라이브러리를 업데이트해도 되지 않았다. `Qwen3-8B`로 교체하자 성공했다.

**코드** [Model.py:19-33](../src/Model.py#L19-L33)

### A-2. 기억을 Graph RAG로

일지에 적은 Vector RAG의 한계는 문장 단위로 잘라 저장하면 맥락, 흐름, 감정의 연결이 깨진다는 것이다. 예시로 "(감정: 화남) 그렇지 밥은 맛있지" 같은 대화가 저장될 수 있다고 적었다. → **[본문 4.1](실험기록.md#41-기억을-문장으로-저장하면-안-되는-이유)**

### A-3. DB를 Neo4j로

인메모리를 다른 것으로 바꿔야 해서 Chroma를 골랐다가, 기억의 연속성과 관계성을 파악하기 쉬운 Graph RAG로 하기로 하면서 Neo4j로 바꿨다. LangChain으로 RAG를 만드는 것도 계획에 있었지만 최종 구현에는 남지 않았다. → **[본문 4.2](실험기록.md#42-chroma에서-neo4j로)**

대화가 많이 쌓이면 어떻게 감당할지, 애초에 그 정도로 쌓일지 따져본 뒤, 모든 대화를 DB에 넣고 시간에 따른 노드의 삭제를 고려하기로 했다. → **[본문 4.4](실험기록.md#44-모든-대화를-저장하고-나중에-잊게-한다)**

### A-6. 세션 경계 = 대화창 접속~종료

세션 기준으로 시간, 대화 주제, 대화의 개수를 후보로 놓았다. 주제 기준은 주제를 판정하려면 모델을 또 돌려야 하고, 날짜 기준은 자정을 넘기는 대화나 하루를 건너뛰는 경우가 걸렸다. 한 세션의 대화를 모두 잊어도 상관없지 않을까, 결국 한 대화의 흐름 내에서의 연속성만 지키면 되니까, 라고 보고 대화창 접속부터 종료까지를 세션으로 묶었다. → **[본문 4.3](실험기록.md#43-저장-단위를-무엇으로-볼-것인가)**

### A-7. 기억 강도 공식

`|Δ감정|·6.0 + |감정|·3.0 + random(0,1) + 2.0`. 일지에는 강도에 넣을 값으로 그때의 감정 변화 수치와 감정의 절대값, 그리고 랜덤값을 적었다. 랜덤값을 넣은 이유는 적혀 있지 않다. → **[본문 5.1](실험기록.md#51-기억-강도)**

커밋에 남은 가중치는 1.0 / 0.5(2/15) → 4.0 / 2.0 + 기본값 2(2/19) → 6.0 / 3.0(2/27)이다. 일지에는 "기억 강도 가중치들을 2배씩 올림"과 "기본 기억 강도를 추가했음"이 적혀 있고, 마지막 6.0 / 3.0으로의 변경은 기록이 없다. → **[본문 5.6](실험기록.md#56-튜닝-기록)**

**코드** [Rag.py:132-137](../src/Rag.py#L132-L137)

### A-8. 노드 삭제 시 NEXT 재연결

일지에는 노드가 삭제되면 대화의 흐름이 끊긴다는 문제를 적었고, 그 뒤에 적은 해법은 대화를 세션으로 묶어 저장하는 것이었다. 코드에는 별도로, 약해진 노드를 지우기 전에 그 이전 노드와 다음 노드를 `NEXT`로 다시 잇는 처리가 첫 커밋부터 들어 있다. → **[본문 5.3](실험기록.md#53-삭제된-기억의-자리를-잇는-문제)**

**코드상 한계** 재연결 쿼리는 앞뒤 노드가 **모두 있을 때만** 동작한다. 사슬의 처음이나 끝에 있는 약한 노드는 재연결 없이 삭제된다.

**코드** [Rag.py:237-243](../src/Rag.py#L237-L243)

### A-9. 세션 요약 노드

일지에는 세션이 끝날 때 해당 세션의 대화를 요약해서 저장할 수도 있겠다고 적었고, 세션 안에 요약 노드를 추가했다. → **[본문 5.4](실험기록.md#54-세션-요약-노드)**

**코드** 요약 노드에는 강도 값이 없고 삭제 대상도 아니다. 검색은 `Turn`의 벡터 인덱스만 조회하고 `Summary`에는 임베딩이 없어, 요약은 저장만 되고 검색되지 않는다. [Rag.py:67-88](../src/Rag.py#L67-L88)

### A-10. 감정 = 단일 스칼라 + 지수 곡선

코드 주석에 적힌 성질은 `(target − valence)`를 곱해 ±1.0을 넘지 않는다는 것, 그리고 intensity가 낮으면 factor가 거의 0이라 변화가 거의 없다는 것이다. → **[본문 6.1](실험기록.md#61-몇-개의-축으로-둘-것인가)**

**검토한 대안** 다차원 감정은 감정의 중복을 어떻게 구현할지, 시간이 얼마나 걸릴지 몰라 긍정·부정으로 일반화했다. arousal 축은 GPT가 제안했고, 에너지가 어떻게 증가하고 감소하는지가 걸려 MVP에서 뺐다. 감정 벡터와 모멘텀을 두는 안도 적었지만 구현되지 않았다.

**코드** [Emotion.py:29-34](../src/Emotion.py#L29-L34)

### A-11. 출력을 JSON 4필드로 고정

**일지에 적힌 과정** 모델의 출력 방법을 정해야 했다. JSON으로 출력하게 하는 것이 마음에 들지 않아 plain text로 감정 변화와 발언을 받는 방법도 적었지만, JSON 구조로 `emotion_delta`와 `utterance`를 출력하게 하기로 했다.

thinking 모드를 끄고 JSON에 `think` 컬럼을 추가하는 것이 어떤 차이인지 물었고, GPT는 의도에 더 어울리는 것이 `think` 컬럼이라고 답했다. 이후 thinking 모드를 사용하니 대화가 더 잘 이어지는 것 같았고, 추론 시간은 두 배 이상이 됐지만 대화가 된다는 것이 중요하다고 적었다. `think`와 `utterance` 내용이 비슷해지는 문제는 프롬프트를 고쳐 아마 해결됐다고 적었다.

**코드** 현재 출력 필드는 `emotion_direction` · `emotion_intensity` · `think` · `utterance`이고, thinking 모드도 켜져 있다. `emotion_delta`에서 방향과 강도로 바뀐 이유는 일지에 적혀 있지 않다. [Model.py:74-114](../src/Model.py#L74-L114) — `</think>` 토큰(151668) 기준으로 사고 부분을 잘라낸다. [system_prompt.txt](../src/prompts/system_prompt.txt)

### A-12. 프롬프트를 3단으로 분리

**일지에 적힌 과정** 감정을 system prompt에 넣으면 기억도 system에 넣어야 해서, 프롬프트를 정적이 아니라 동적으로 받아야 했다. 선택지는 두 가지였다. system prompt와 user prompt를 동적으로 받아 요약과 대화를 하나의 함수로 쓰는 것, 그리고 함수를 분리하고 대화 함수만 감정과 기억을 인자로 받는 것. 세 번째 선택으로 갔다. 함수는 따로 두고, system prompt · context prompt · user prompt로 나눠 감정과 기억을 context prompt에 넣는다.

처음에는 context prompt를 system prompt 맨 끝에 두었다. 이후 context가 user prompt와 연관성이 깊다는 이유로 `system → history → context → user` 순서로 바꿨다(A-13).

**코드** [Model.py:52-71](../src/Model.py#L52-L71). 프롬프트 파일화는 커밋 `b4e2fd1`, 순서 변경은 `a6b7ac1`

### A-13. context의 role을 user로

context의 role을 system으로 하면 뒤 system이 앞 system을 미묘하게 덮고, assistant로 하면 과거에 자기가 했던 발언이라고 착각한다는 답을 들었다. 그래서 role은 user로 하되 구조화하기로 했다. → **[본문 7.3](실험기록.md#73-기억-포맷-변경)**

**코드** [Model.py:59-71](../src/Model.py#L59-L71), 커밋 `a6b7ac1`

### A-14. 기억 포맷을 회고 서술로

일지에는 모델이 기억을 현재 대화와 헷갈리는 것 같다고 적었다. 프롬프트 순서를 바꾸고 경계선을 넣고 안내를 강화했지만 효과가 없었고, 기억 포맷이 `User/AI` 식이라 history와 헷갈리는 것 같다는 답을 들었다. 포맷을 바꾼 뒤 "확실히 효과 있음"이라고 적었다. → **[본문 7.3](실험기록.md#73-기억-포맷-변경)**

### A-16. 검색 임베딩에 최근 n턴을 포함

**문제** 사용자 입력만 기준으로 검색하니 단답 위주의 대화에서 기억을 못 가져오는 경우가 생겼다.

**일지에 적힌 과정** 검색에 쓰는 임베딩에 최근 대화 n턴을 넣어야 할지 묻고, 그러면 주제가 갑자기 바뀌는 상황은 어떻게 되는지 적었다. GPT가 제시한 방법(범용어 가중치를 낮추는 하이브리드 검색, 저장 시점에 명사를 추출해 점수를 매기는 전처리, 범용어를 제거하고 임베딩, 최근 턴 평균 임베딩, 명사 전용 임베딩) 중 최근 턴을 반영하는 방법이 가장 간단하다고 봤다. 갑자기 대화 주제가 바뀌는 상황에서는 잘못 가져올 수 있다는 점을 적고, 일단 간단하니 먼저 구현해보고 결과를 지켜보기로 했다.

**이후** 최근 대화 기반 검색만 쓰니 주제가 바뀔 때 관련 기억을 바로 가져오지 못하는 것 같다고 적었고, A-17로 이어졌다.

**코드** 최근 2턴(4개 발화)과 현재 입력을 이어 붙여 임베딩한다. [Pipeline.py:57-59](../src/Pipeline.py#L57-L59), 커밋 `41f977a`

### A-17. 하이브리드 검색 — 명사 키워드 + 맥락 재정렬

**문제** 전에 클럽에 간다고 이야기했는데 "어제 클럽 다녀왔어"에서 검색하지 못했다. 맥락 유사도 검색이 아니라 명사에 대한 추가 검색이 필요하다고 봤다.

**일지에 적힌 과정** 키워드로만 검색하면 너무 많은 대화문이 나올 것 같았고, 키워드로 하드 필터링하면 동의어, 추상 표현, 은유 표현 같은 대화들을 놓친다. 그래서 명사 임베딩으로 검색한 뒤 대화 맥락으로 필터링하기로 했다. 명사 벡터 검색은 범위를 넓게 하고, 대화 맥락은 아예 관련 없는 대화만 쳐내는 용도로 쓴다.

**코드** 형태소 분석(Kiwi)으로 일반명사·고유명사를 뽑고, 명사별로 벡터 검색을 돌려 상위 3개씩 후보를 모은 뒤, 대화 맥락과의 코사인 유사도로 재정렬해 상위 5개를 기억에 넣는다. [Pipeline.py:61-79](../src/Pipeline.py#L61-L79), [Rag.py:207-223](../src/Rag.py#L207-L223), 커밋 `73428bb`

### A-18. 기억 강도에 따라 시간 해상도를 저하

일지에는 "어제"라고 말해도 AI가 그 기억이 현재 기준으로 어제인지 판단하지 못한다고 적고 시각을 넣기로 했다. 과거 데이터에 시·분까지 굳이 넣어야 하나, 시는 애매하고 분은 굳이 필요 없다고 보고, 기억 강도 풍화에 따라 동적으로 단순화하기로 했다. 코드는 강도에 따라 기억에 넣는 시각을 분·시·일·월 단위로 줄인다. → **[본문 5.5](실험기록.md#55-기억이-흐려지면-시간도-흐려진다)**

**코드** [Pipeline.py:140-150](../src/Pipeline.py#L140-L150), 커밋 `6444a11`

### A-19. 강화학습을 현 단계에서 보류

일지에는 벌점이 부정적 경험에서 이유를 남기지 않고 행동을 하지 않게만 만들며, 부정적 감정에 벌점을 주면 학습 후기에는 부정적 감정을 표출하지 못하는 상황이 만들어질 가능성이 크다고 적었다. 일지 마지막에는 "현재 강화학습을 넣는것은 이르다"고 보고, 기본 캐릭터를 QLoRA 파인튜닝으로 간단히 학습시켜 놓는 것과 기존 기억 검색을 강화해 회피·배움 현상이 발생하는지 확인하는 것을 방향으로 정리했다. → **[본문 3장](실험기록.md#3-벌점으로-가르칠-수-있는가--강화학습을-미룬-이유)**

**검토한 대안** 실시간 강화학습 대신 평소에는 추론 모드로 데이터를 모으고 나중에 학습시키는 방법, 자기 보상 모델(어댑터 분리, 오버테크라며 접어둠), 사용자 입력 기반 보상(단독으로는 쓰지 않고 보상 구조의 한 항으로 넣기로 함)

## D. 실행 및 재현

### 대화 시스템

**필요 환경** Python 3.12+ · CUDA GPU · Docker (Neo4j)

모델은 `Qwen/Qwen3-8B`을 bitsandbytes nf4로 4bit 로드하고, 임베딩은 `Qwen/Qwen3-Embedding-0.6B`를 CPU에서 돌린다. 임베딩을 CPU에 둔 이유는 [본문 4.2](실험기록.md#42-chroma에서-neo4j로)에 있다.

**1. Neo4j 실행**

```bash
docker run -d \
  -p 7687:7687 -p 7474:7474 \
  -v ./DB:/data \
  -e NEO4J_AUTH=neo4j/password \
  neo4j:latest
```

**2. 환경 변수** — 프로젝트 루트에 `.env`

```
NEO4J_URI=bolt://localhost:7687
NEO4J_USERNAME=neo4j
NEO4J_PASSWORD=password
```

**3. 의존성 설치 및 실행**

```bash
pip install -r requirements.txt
cd src && python app.py
```

브라우저에서 `http://localhost:7860` 접속. 대화창을 닫으면 세션이 종료되고, 대화가 있었다면 요약 노드가 생성된다.

### 로그 정량 분석

부록 B의 수치는 이 스크립트로 재현된다. 표준 라이브러리만 쓰므로 별도 설치가 필요 없다.

```bash
python tools/analyze_logs.py                 # logs_1/, logs/ 자동 탐색
python tools/analyze_logs.py <디렉터리> ...    # 디렉터리 지정
```
